interrupt()方法

很多人看到 interrupt() 方法，认为“中断”线程不就是让线程停止嘛。实际上， interrupt() 方法实现的根本就不是这个效果，

interrupt()方法更像是发出一个信号，这个信号 会改变线程的一个标识位属性（中断标识），对于这个信号如何进行响应则是无法确定的（可以有不同的处理逻辑）。很多时候调用 interrupt() 方法非但不是为了停止线程，反而是为了让线程继续运行下去。设置线程中断不影响线程的继续执行

interrupt() 方法的作用：设置该线程的中断标志为 true 并立即返回（该线程并不一定是当前线程，而是指调用该方法的 Thread 实例所代表的线程），但线程实际上并没有被中断而会继续向下执行，会由用户自己决定要不要终止线程以及什么时候终止线程；如果线程因为调用了 wait 系列函数、join 方法或者 sleep 方法而 被阻塞挂起，其他线程调用该线程的 interrupt()方法会使该线程抛 InterruptedException 异常而返回。

interrupt()是实例方法，是调用该方法的对象所表示的那个线程的 interrupt()。

boolean isInterrupted()

isInterrupted()方法的作用：只判断此线程是否被中断 （此线程指的是调用isInterrupted()方法的Thread实例所代表的线程），是则返回true，否则返回false，不清除中断状态。

如果线程还没有 start 启动，或者已经消亡，那么返回依然是 false。中断状态只代表是否有线程调用中断方法，并不代表这个线程是否在运行。

isInterrupted()是实例方法，是调用该方法的对象所表示的那个线程的isInterrupted()

static boolean interrupted()

interrupted()方法的作用：判断当前线程是否被中断（检查中断标志）（注意，这里指的是当前线程，不是调用该方法的Thread实例所代表的线程），返回一个boolean（当前的中断标志），被中断则返回true，否则返回false。并清除中断状态（将中断标志设置为false）。因为该方法是static方法，内部是获取当前调用线程的中断标志而不是调用interrupted()方法的实例对象的中断标志。

这里有一点需要注意，调用interrupted()方法时，它会先记录下当前的中断标志位，然后才会去清除中断状态，也就是将中断标志位设置为false，最后返回之前记录的中断标志位。也就是说如果在调用interrupted()方法前当前线程已经中断了（中断标志为true），那么第一次调用interrupted()方法返回的就是true，但是第一次调用之后当前线程的中断标志就被interrupted()方法设置为false了，所以第二次再调用interrupted()方法时中断状态已经被清除，将返回一个false。

关于这三个方法，

interrupt()是给线程设置中断标志；

interrupted()是检测中断并清除中断状态；

isInterrupted()只检测中断。

还有重要的一点就是interrupted()作用于当前线程，

interrupt()和isInterrupted()作用于此线程，即代码中调用此方法的实例所代表的线程

方法 类型 作用对象 是否清除中断状态？
thread.interrupt() 实例方法 thread 实例所代表的线程 -
thread.isInterrupted() 实例方法 thread 实例所代表的线程 否
Thread.interrupted() 静态方法 当前正在执行这行代码的线程 是

LockSupport

Park

要permit为1或者中断状态为true，那么执行park就不能够阻塞线程。park只可能消耗掉permit，但不会去消耗掉中断状态。所以能够使用park()阻塞的线程，它的premit一定为0，并且中断状态一定是false。调用过park()的线程，不管是有没有进行阻塞，不管是因为中断而结束的阻塞，还是因为unpark而结束的阻塞，只要调用了park()方法，到最后permit一定为0（因为在开始和结束位置都去消费了permit）

UnPark

unpark一定会将permit置为1，如果此时线程处于阻塞状态，再将其唤醒。从实现可见，无论调用几次unpark，permit只能为1。

调用过unpark()的线程，最后permit一定为1

parkNanos

使当前线程在指定的时间内暂停执行，但与 Thread.sleep 不同的是，它通常与锁或其他同步机制一起使用，更灵活。

  • 可以与 LockSupport.unpark 方法配合使用，允许线程在等待时被提前唤醒。

  • 通常用于更复杂的线程同步场景，如自旋锁、条件变量等。

  • 如果线程被中断，也会抛出 InterruptedException。

  • 精度更高，支持纳秒级别的暂停时间。

Sleep

Thread.sleep

让当前线程暂停执行指定的时间（以毫秒为单位）。在暂停期间，线程不会释放任何锁（如果它持有锁的话）。

简单易用，适合简单的线程暂停场景。

不会释放锁，因此如果线程在持有锁时调用 Thread.sleep，其他线程无法获取该锁。

如果线程被中断（调用 interrupt 方法），会抛出 InterruptedException。

  • Thread.sleep：

    • 适用于简单的线程暂停，如在日志输出中添加延迟，或者在轮询中减少 CPU 占用。

  • LockSupport.parkNanos：

    • 适用于需要更精细控制线程暂停和唤醒的场景，如实现自旋锁、条件变量等

  • 如果线程在调用 Thread.sleep 或 LockSupport.parkNanos 时被中断，需要正确处理 InterruptedException，否则可能会导致线程异常终止。

  • 在多线程环境中，使用 Thread.sleep 时要特别注意锁的释放情况，避免造成死锁

总结11.3—-11.6

park调用后一定会消耗掉permit，无论unpark操作先做还是后做（看上面对park讲解的源码中，在park开始和结尾都执行了一遍消耗permit的操作，所以无论unpark操作在park操作之前还是之后，只要是调用了park，那么现成的permit最后一定是0）。
如果中断状态为true，那么park无法阻塞
unpark会使得permit为1，并唤醒处于阻塞的线程
interrupt()会使得中断状态为true，并调用unpark
sleep() / wait() / join()调用后一定会消耗掉中断状态，无论interrupt()操作先做还是后做（看上面对sleep讲解的源码中，在sleep开头和结尾都执行了一遍消耗中断状态的代码，所以无论interrupt操作在sleep之前还是之后，只要是调用了sleep，那么线程的中断状态最后一定是false）
关于这一点，“如果中断状态为true，那么park无法阻塞”。在AQS源码里的acquireQueued里，由于acquireQueued是阻塞式的抢锁，线程可能重复着 阻塞->被唤醒 的过程，所以在这个过程中，如果遇到了中断，一定要用Thread.interrupted()将中断状态消耗掉，并将这个中断状态暂时保存到一个局部变量中去。不然只要遇到中断一次后，线程在抢锁失败后就无法阻塞了
