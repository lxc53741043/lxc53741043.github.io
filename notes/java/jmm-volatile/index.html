Java 内存模型与 volatile

整理 Java 内存模型，以及 volatile 的可见性与禁止指令重排序语义。

JAVA内存模型

关于主内存与工作内存之间具体的交互协议，Java虚拟机定义了8种原子操作：

  1. lock（锁定）：作用于主内存的变量，它把一个变量标识为一条线程独占的状态。
  2. unlock（解锁）：作用于主内存的变量，它把一个处于锁定状态的变量释放出来，释放后的变量才可以被其它线程锁定。
  3. read（读取）：作用于主内存的变量，它把一个变量的值从主内存传输到线程的工作内存中，以便随后的load动作使用。
  4. load（载入）：作用于工作内存的变量，它把read操作从主内存中得到的变量值放入工作内存的变量副本中。
  5. use（使用）：作用于工作内存的变量，它把工作内存中一个变量的值传递给执行引擎，每当虚拟机遇到一个需要使用的变量的值的字节码指令时，执行这个操作。
  6. assign（赋值）：作用于工作内存的变量，它把一个执行引擎接收到的值赋给工作内存的变量，每当虚拟机遇到一个给变量赋值的字节码指令时，执行这个操作。
  7. stroe（存储）：作用于工作内存的变量，它把工作内存中一个变量的值传送到主内存中，以便随后的write操作使用。
  8. write（写入）：作用于主内存的变量，它把store操作从工作内存中得到的变量的值放入主内存的变量中。

Volatile

原子性

定义：一个操作不可拆分、不被中断，要么全部执行，要么都不执行。

volatile并不能保证原子性

synchronized关键字可以保证原子性，因为被synchronized修饰的方法或代码块，在进入之前都加了锁，同一时刻，有且仅有一个线程能执行被“锁”住的代码片段，这就保证了它内部的代码可以全部被执行，所以它具备原子性（基于monitorenter和monitorexit指令实现）

ps：数据库中ACID的原子性指的是“要么都执行要么都回滚”，这是两个不同的概念

线程可见性

定义：指多个线程之间共享数据的可见性。即当一个线程修改了共享变量时，其它线程能立即看到这个修改。

指令重排序

理解 DCL 中 volatile 的必要性：指令重排序问题

instance = new Config() 这行代码的问题不在于类加载机制，而在于 指令重排序 和 内存可见性 问题。

对象创建过程的分解

当执行 instance = new Config() 时，JVM 实际上会执行多个步骤：

  1. 分配内存空间：为 Config 对象分配内存
  2. 初始化默认值：将对象的字段设置为默认值（0、false、null等）
  3. 执行构造方法：调用 Config 的构造方法，进行真正的初始化
  4. 赋值引用：将 instance 变量指向新创建的对象

指令重排序的问题

关键问题在于：JVM 和处理器可能会对这些步骤进行重排序优化，可能会按照这样的顺序执行：

  1. 分配内存空间
  2. 赋值引用（此时 instance 不为 null）
  3. 执行构造方法（真正的初始化）

这种重排序在单线程环境下没有问题，但在多线程环境下会导致严重问题。

多线程场景下的问题

假设没有使用 volatile，两个线程同时调用 getInstance()：

  1. 线程 A 进入同步块，开始执行 instance = new Config()
  2. JVM 重排序指令：先分配内存，然后将引用赋值给 instance，但尚未执行构造方法
  3. 此时线程 B 检查 if (instance == null)，发现 instance 不为 null
  4. 线程 B 直接返回 instance，但此时对象尚未完全初始化！
  5. 线程 B 开始使用这个”半成品”对象，可能导致不可预知的行为

volatile 如何解决这个问题

使用 volatile 关键字修饰 instance 变量时：

  1. 禁止指令重排序：确保对象完全初始化后才将引用赋值给 instance
  2. 保证内存可见性：确保一个线程对 instance 的修改对其他线程立即可见

具体来说，volatile 会在写操作前后插入内存屏障，防止编译器和处理器对指令进行重排序。
